# Agent workflow opportunities and validation

**Reuse-first is a conservative starting hypothesis, not a proven product priority.** The target user is a developer or coding agent with a working host toolchain and several native services; the job is to edit, reach the intended ready application, check it, diagnose failures and clean up without disturbing another task. Retained sessions, JSON discovery, generation-aware restarts, bounded journals and fresh verification already cover much of that job. Correct documentation is justified by verified inaccuracies; whether a version-matched CLI/browser recipe is the best opportunity remains unmeasured. Managed checks on retained sessions are a real public capability gap, but their incremental value and per-check cleanup safety remain unproven. Recommend one separately approved compatibility-and-workflow pilot; **no new feature for the selected job is a successful outcome**, not proof that other users have no unmet needs.

**Scope and method.** Study date: **2026-10-19**. This synthesis reads all [new research notes](../research_notes/Agent%20workflow%20opportunities%20and%20validation/), the [earlier study](Local%20development%20agent%20opportunities.md) and its [notes](../research_notes/Local%20development%20agent%20opportunities/), with narrow primary-code rereads. The inspected code is **main@7a9e93d3361278e72d72672f6253773c96e73ad7**, tagged **v1.10.0**. This is primary-source desk research and static inspection, not interviews, runtime tests, measured demand or measured speed gains. Test-source assertions are not passing test results. Documentation-only corrections from the [adversarial review](Adversarial%20review%20of%20agent%20research.md) are applied here and in the supporting notes; no pilot has run. Earlier hypotheses remain hypotheses; agent ubiquity is not an adoption finding.

## Existing contracts already cover most of the development loop

The [baseline audit](../research_notes/Agent%20workflow%20opportunities%20and%20validation/proc-compose-baseline.md) establishes a reuse baseline, not a runtime certification. proc-compose coordinates native processes; application tests still own business assertions, authentication, fixtures and loaded-code evidence.

| Need | Existing capability and source | Boundary |
|---|---|---|
| Discover and preflight | Offline `agent-guide`, `config check/plan/schema`, `sessions --json`; [internal/agentguide/GUIDE.md:107–153](../../internal/agentguide/GUIDE.md#L107-L153). | Static plans start nothing; owner labels are descriptive. |
| Retain, observe and restart | `up --silent --wait-ready --json`, `status --json`, targeted `restart --wait-ready`; [internal/agentguide/GUIDE.md:89–111](../../internal/agentguide/GUIDE.md#L89-L111), [cmd/proc-compose/main.go:685–705](../../cmd/proc-compose/main.go#L685-L705). | Failed readiness leaves the daemon running. Plain restart acknowledges intent, not replacement readiness. |
| Own a fresh verification | `verify --json -- PROGRAM ARG…` acquires a fresh session, waits, checks, monitors required services and cleans up; [internal/verify/operation.go:466–497](../../internal/verify/operation.go#L466-L497). | Occupied sessions are refused, not attached or stopped; fresh processes do not reset databases. |
| Diagnose boundedly | Journal filters/cursors, explicit page gaps/truncation and live-versus-retained `why`; [Sessions and logs](../../docs/sessions-and-logs.md#logs-for-coding-agents). | Defaults bound event data to 50 events/64 KiB plus envelope. Retained `why` is not complete-history proof. Logs are untrusted and not secret-redacted. |
| Separate worktree instances | Config-path/session identity, instance/resource/port leases and resolved URLs; [internal/paths/paths.go:18–28](../../internal/paths/paths.go#L18-L28), [internal/session/session.go:34–99](../../internal/session/session.go#L34-L99). | Cooperation is not filesystem, database or credential isolation. |
| Return a correctness contract | `verify` exits 0 only for successful startup/check/cleanup with persisted receipt; 1 for failures, 2 for pre-start refusal/usage/config, 130 for interruption; [Verified runs](../../docs/verify.md). | Environment and required-service verdicts remain distinct from check exit. |

Machine-readable coverage is substantial but not uniform. `verify --json` returns one bounded object for normal operation and semantic refusals after flag parsing, but parser errors can return exit 2 with plaintext stderr and empty stdout, even after `--json`. Inspect exit/stderr before decoding ([verify_cli_test.go:109–112](../../cmd/proc-compose/verify_cli_test.go#L109-L112), assertions read, not run). Other failed commands can also emit stderr only. Restart/reload expose human results despite existing structured internal acknowledgments. Reload can return **partial with exit 0**, so zero alone does not establish full application of configuration ([Verified runs](../../docs/verify.md), [cmd/proc-compose/main.go:728–781](../../cmd/proc-compose/main.go#L728-L781), [internal/ipc/ipc.go:253–284](../../internal/ipc/ipc.go#L253-L284)).

## Browser ownership and fresh identity determine what a pass means

Official workflows already support command execution and observation. OpenAI's [Integrated terminal](https://developers.openai.com/codex/integrated-terminal.md) page describes a project/worktree-scoped ChatGPT desktop terminal, not universal Codex CLI lifetime; the [Worktrees](https://developers.openai.com/codex/app/worktrees) guide supports parallel chats, not automatically isolated application state. Claude's [Tools reference](https://code.claude.com/docs/en/tools-reference.md) supports background servers, bounded output and task stopping, with lifetime depending on owner and execution mode. Claude Code Bash exports do not persist between separate commands. Conversation history therefore cannot substitute for current supervisor evidence.

**Name the accountable owner per resource, with explicit delegation and reuse.** Playwright's [Web server](https://playwright.dev/docs/test-webserver) supports multiple servers, readiness waits, endpoint reuse, output routing and shutdown of commands it launches; it does not adopt reused servers for teardown. Playwright may own a foreground proc-compose parent which owns its services, if signal/cleanup behavior is verified. Alternatively it can consume a retained stack's resolved endpoint without a competing launcher. In URL mode, reuse/refusal follows the documented HTTP availability test, not every listening process; URL and output waits combine with OR, not AND. Neither availability nor `reuseExistingServer` establishes checkout identity.

The concrete loop begins with an edit and explicit absolute config/session selection. Inspect `sessions/status`, confirm task ownership, then start or reuse the intended stack and wait for application-relevant probes, not sleeps. Pass the same resolved URLs to browser and API assertions. On failure, request finite `why`/journal pages for the observed `(run_id, process, generation)`, retaining cursor and truncation evidence. Restart only the changed service when needed, wait for the acknowledged new generation, then repeat the application assertions. Finally, stop only the owned session in a failure-safe cleanup path, including after unsuccessful startup ([internal/agentguide/GUIDE.md:89–135](../../internal/agentguide/GUIDE.md#L89-L135)).

Identity needs more than a PID or source SHA. Readiness socket attribution exists on Linux/Windows, not macOS. Fresh `verify` refuses attributed cross-live-session answers by default; Windows does so only on another session's leased port, and macOS does not attribute or refuse. Outside-session or unattributable answers need additional policy, and unattributable evidence is not a rejection guarantee. Probe ownership observes one socket at one moment, not every browser connection. Existing environment reports can capture real build/fixture/worker observations, and `--require-environment` rejects absent evidence; **source revision is provenance, not loaded-code proof** ([Verified runs](../../docs/verify.md), [Environment reports](../../docs/verify.md#environment-reports)). Re-read identity before mutation; optional expected-run guards would address stale intent, not authenticate callers.

Worktree safety also requires resolved port/environment propagation, separate writable uploads/build outputs and database/queue namespaces, or explicit leases that serialize shared resources. Copying an ignored environment file can preserve shared targets. Existing endpoint variables and `${session.dir}` are reusable, but unrelated programs can race application binds ([Sessions and logs](../../docs/sessions-and-logs.md)). Validate access from the actual shell **and browser**: Codex's [Agent approvals & security](https://developers.openai.com/codex/agent-approvals-security.md) distinguishes sandbox and network policy; Claude's [Configure permissions](https://code.claude.com/docs/en/permissions) says written instructions do not change enforced permissions. A supervisor outside the sandbox must not be used as an approval bypass; its control interface is a capability boundary.

Cleanup is scoped, not universal. Live stop consumes a managed-process termination verdict; escaped groups and legacy/crash/platform paths have limits, including a documented macOS PID-reuse hazard and readable legacy force-stop warnings despite exit 0 ([cmd/proc-compose/main.go:461–494](../../cmd/proc-compose/main.go#L461-L494), [Stop a running daemon](../../docs/cli.md#stop-a-running-daemon)). Neither database reset nor worktree deletion proves process cleanup.

## Adjacent tools narrow the opportunity to dependable native contracts

The [bounded alternatives comparison](../research_notes/Agent%20workflow%20opportunities%20and%20validation/alternatives-and-opportunities.md) compares documented semantics, not runtime reliability or market share. “Not established” means absent from this source sample, not absent from a product.

| Alternative | Established overlap | Substitute or complement |
|---|---|---|
| **process-compose** | Readiness/liveness, dependencies, recovery, logs, REST/OpenAPI and an MCP server with optional project controls ([process-compose README](https://raw.githubusercontent.com/F1bonacc1/process-compose/main/README.md)). | Closest native-process substitute. Per-worktree leases, bounded cursor contracts and verified descendant cleanup are not established here. MCP alone is not unique in this sample. |
| **Docker Compose** | Project scoping, logs/events, one-off commands and dependency conditions for healthy services or successfully completed tasks ([docker compose CLI reference](https://docs.docker.com/reference/cli/docker/compose/), [Control startup and shutdown order in Compose](https://docs.docker.com/compose/how-tos/startup-order/)). | Substitute for containerized stacks; complement for infrastructure. Preserve container networking/volume ownership; host ports and data policy still need isolation. |
| **Tilt** | Native `local_resource` commands/servers, dependencies, readiness and file triggers; `ci_settings` deadlines apply to `tilt ci` ([Tilt API reference](https://docs.tilt.dev/api.html)). | Broader development-loop substitute, including Compose integration. Build/update commands default to serial execution because shared filesystem mutations can race; this is not a ban on overlapping servers. Do not rebuild its update graph. |
| **devenv** | Native readiness/control, named ports, shutdown/guardian cleanup; task DAGs can skip execution using status/input checks and restore cached outputs; task-scoped process cleanup ([Processes](https://devenv.sh/processes/), [Tasks](https://devenv.sh/tasks/)). | Provisioning complement and orchestration substitute. Ports release before spawn; attaching uses original manager configuration. Status predicates themselves are not cached; reproducibility is not loaded-code proof. |

The inferred best fit is native multi-service projects with existing toolchains and repeated branch-local work. That segment is a hypothesis. Where Playwright, Compose, Tilt or devenv already meets ownership/readiness/cleanup needs, replacing it adds migration cost without demonstrated value.

## Rank reuse above new execution surfaces

These are **qualitative value/fit hypotheses**, not demonstrated priority or speed rankings. Source confidence describes the existence of a contract or gap; confidence in adoption and effectiveness remains low throughout. Effort/risk is a design-dependent engineering judgment, not measured implementation cost.

| Order / option | Evidence and confidence | Effort / risk; decision |
|---|---|---|
| Default: **no new feature** | High confidence that existing mechanisms cover much of the loop. | Lowest; retain current workflow if adequate. |
| First: **existing CLI + documentation** | High confidence in two inspected documentation errors, now corrected; workflow benefit unmeasured. | Low hypothesis; validate a short owner/endpoint/cleanup recipe before expanding interfaces. |
| First: **test-harness integration** | High confidence Playwright can own launched resources; application compatibility unknown. | Low–medium hypothesis; prove external-endpoint support without weakening fixture guards or duplicating launchers. |
| Conditional: **focused contract changes** | High confidence in public mutation JSON/expected-run gaps; no wrong-run incident established. | Medium; extend existing acknowledgments only after reproducible parsing/stale-intent failure survives correct CLI use. |
| Conditional: **isolated worktree improvements** | Existing leases/ports are established; end-to-end data isolation is not. | Medium, safety-sensitive; start with application provisioning and existing variables, not another allocator. |
| Defer: **retained managed checks** | Public operation absent; incremental ownership/evidence need unmeasured. | Medium–high; require per-check cleanup and concurrency contracts before design approval. |
| Defer: **MCP** | No named client here requires it; competitor support means it is not uniquely differentiating, not that it lacks utility. | Cost depends on transport, authority and reuse; stdio need not expose a network listener. Consider a thin adapter if a named client or demonstrated usability need justifies it. |

The approved documentation slice corrects the runtime fallback and custom-log descriptions in [Daemon file paths](../../docs/cli.md#daemon-file-paths): current source prefers per-user cache before temp and queries an independent structured journal ([internal/paths/paths.go:31–49](../../internal/paths/paths.go#L31-L49), [cmd/proc-compose/logs.go:48–73](../../cmd/proc-compose/logs.go#L48-L73)). It also clarifies JSON parser exceptions and extends the existing [agent/browser workflow](../../docs/sessions-and-logs.md#agent-and-browser-test-workflow). These are documentation changes, not runtime fixes. MCP cost remains unmeasured; [process-compose's MCP documentation](https://f1bonacc1.github.io/process-compose/mcp-server/) demonstrates stdio as well as SSE.

**Retained checks need more than exposing `RunCheck`.** The dispatcher has restart/reload/shutdown only. `RunCheck` already performs ordinary group teardown on cancellation, and its shared executor also handles natural leader exit; it is incorrect to claim cleanup is absent. But blocked reap can return `HandedOff` for terminal whole-stack sealing, while survivor/escape evidence is recorded outside an independent per-check verdict. That does not prove cleanup while services remain retained ([internal/runner/runner.go:607–684](../../internal/runner/runner.go#L607-L684), [internal/runner/check.go:80–158](../../internal/runner/check.go#L80-L158), [internal/runner/lifecycle.go:674–687](../../internal/runner/lifecycle.go#L674-L687), [internal/runner/lifecycle.go:782–814](../../internal/runner/lifecycle.go#L782-L814)). Required-service monitoring, repeated-check identity/history, admission during mutations and bounded results also need orchestration; the serial command acknowledgment has a 30-second window. Reuse runner/verifier/IPC/journal/lease layers; reject a parallel runner, log reader, report schema, generic task language or universal attestation engine.

## Canonical pilot

The historical record ([local workflow and coverage.md:17–44](../research_notes/Local%20development%20agent%20opportunities/local%20workflow%20and%20coverage.md#L17-L44)) describes real proc-compose development, useful journals, and a separate Playwright gate owning six servers with guarded resets. Later records report the harness corrected and green checks; the earlier failure is not an outstanding supervisor defect. Its timings are unlike command totals and a startup decomposition without raw overlap spans, **not paired edit/check measurements** ([local workflow and coverage.md:110–139](../research_notes/Local%20development%20agent%20opportunities/local%20workflow%20and%20coverage.md#L110-L139)). Current receipts, lifecycle-critical-path timings, agent interaction latency and retained-reset compatibility are missing.

**This is the single current pilot specification; supporting notes defer to it. Proposed—not executed or authorized:** replay the recorded resident-ID-card photo → QR → download task in a disposable application checkout. Bind three real, owner-selected frontend, API/worker and follow-up edits to exact revisions and existing browser/API assertions. If history cannot supply them, document three actual edits on the next approved task. Repeated green checks are not development iterations, and replay feasibility is not productivity of discovering a change.

First inspect the installed Playwright/harness version and external-endpoint support, then demonstrate that its existing browser check can consume a **proc-compose-managed retained stack** without launching servers or violating fixture/reset requirements. Check browser and shell access, resolved URLs and real application identity. If shutdown is required before every reset, cold startup is itself an acceptance condition, or external targeting is unsupported, stop: retain the test-owned harness. Do not build a parallel harness to manufacture compatibility.

If compatible, freeze **A: the actual working CLI/Playwright workflow**, preserving any legitimate existing reuse, and **B: existing retained proc-compose plus the same check and a concise ownership/endpoint/diagnosis recipe**. Pin exact commands, versions and owners; do not manufacture cold starts in A. Replay the same three edits. Equalize fixture safety, source/build prerequisites, assertions, expected failures, credentials, permissions, deadlines, agent/model versions, initial contexts/prompts and instrumentation; record preparation separately. Lifecycle ownership, retention and guidance form the declared **integration bundle**. Its acceptability and observed interaction cost are the estimand; the components cannot receive separate causal credit. B includes initial startup and final verified stop, with only necessary generation-aware restarts. Fresh `verify` is an alternative, not a third arm; no future API receives credit.

Record versions, revisions, run/generation identity, expected/observed URLs, real-path fixture/build readback, argv, exits, bounded diagnostic pages, tool calls and predefined lifecycle-related retries/interventions. Randomize complete-block order; restore equivalent pre-task snapshots/cache baselines where feasible and report exceptions, while retaining B within its block. Distinguish cold launch from warm reuse. Capture monotonic ready/check/restart/cleanup spans and **complete block wall-clock time**, from before first edit/start through final owned cleanup. Do not sum concurrent durations into elapsed savings. One block per arm cannot remove learning/order/cache confounds: report observations, not causal speedup or general demand. Equal counts may reflect a floor; report **no observed advantage**, not general disconfirmation.

Before execution, approve the following exposures, owners, independent observers, deadlines and postcondition windows, equally offered to A and B. Inventory owned PID/start identities, descendants, endpoints and deliberately retained services. An exit code alone is not a cleanup oracle.

| Exposure | Required observation and limit |
|---|---|
| Normal check and one approved bounded interruption | Observe check-owned children/listeners exit, deliberately retained services survive, and final stop release only owned processes/ports within the declared window. |
| One safe known identity mismatch | Real application-path build/fixture/worker readback rejects the mismatch; echoing supplied expectations is not an oracle. |
| Unrelated control and survivor-detection check | Control remains untouched; the observer detects an approved owned child/listener while alive and its later exit. Group-only observation cannot exclude detached escapees. |

Record **eligible exposures and outcomes per contract**, not three assumed opportunities because there are three edits. Missing exposure means **not exercised/inconclusive**; lost observability or unverified cleanup means unknown, never pass. A future retained-check design must separately prove incomplete-reap handling **at each check boundary**, not only final stack shutdown; this pilot does not establish that guarantee.

Proposed safety gates—not observations—permit zero false identity/cleanup passes or unrelated mutations. Stop immediately on one unsafe/unverified cleanup, foreign mutation, shared-state damage or permission bypass; do not repeat harm to meet a count. Agree materiality before running; no time threshold is supplied by the evidence. Investigate serious safety failures immediately. Escalate a non-dangerous deficit only with an attributable eligible exposure and a separately approved narrow reproduction, not a two-of-three-edit rule. Outcomes are A adequate, B incompatible/rejected, bundle feasible, boundary deficit reproduced, no observed advantage, or inconclusive. If A suffices, B's recipe resolves friction, or lifecycle cost is immaterial, select **no core feature for this job**; unequal correctness rejects that comparison, not all future opportunities.

**Separate optional two-worktree safety gate:** only if parallel operation is part of the selected job, launch two explicitly owned disposable sessions with distinct endpoints/data namespaces, verify fixture separation and wrong-endpoint detection, then stop one and confirm the other survives. Abort on shared-state uncertainty or foreign mutation. This is a bounded isolation gate, not another performance pilot or authorization to reset shared data.

| Stage | Decision gate |
|---|---|
| Research challenge | Confirm exact task, versions, assertions, ownership and approval boundaries; otherwise stop. |
| Compatibility then matched pilot | Run only after separate scoped approval; publish bounded evidence and confounds, including no-feature outcomes. |
| Contract proposal, if necessary | Specify the smallest demonstrated deficit and regression obligations; obtain separate design/implementation approval. |

## Conclusion

The working product hypothesis is that a dependable native-process contract may help across handoffs; this study does not establish the best opportunity or that another command surface adds value. Compatibility failure would itself be useful evidence: it preserves a valid browser gate rather than disguising a weaker warm check as progress. A demonstrated need or boundary failure, not this desk study alone, should motivate a separately approved implementation proposal; **no code or configuration changes are authorized by this study**.
