# Local development agents: failure reports and a lifecycle baseline

> **Historical background — 2026-10-18; relocated for publication on 2026-10-19.** Original wording and citation line labels are retained as historical evidence, not current pilot instructions or fresh verification. Use the [canonical pilot](../../reports/Agent%20workflow%20opportunities%20and%20validation.md#canonical-pilot) and the later municipal reports indexed in the [research README](../../README.md). Any `file://` citations are **local-only evidence**; their referenced files and raw artifacts are not published here.

Research cutoff/access: **2026-10-18**. Read-only research; no local reproduction, service launch, installation, or benchmark was performed. The selected external corpus is exactly **four primary source records**: three vendor-repository issue threads, including their comments/status history, and one official Docker Compose command reference. Comment anchors below are evidence within the corresponding issue, not additional selected reports. Search results were discovery material, not evidence.

## 1. Which concrete failure reports establish repeatable mechanisms?

### Takeaway

The best-supported mechanisms are **termination acknowledgement without effective descendant cleanup** and **agent-visible process state diverging from OS state**. These sources establish bounded historical observations, not prevalence, a current cross-platform defect, or a demonstrated need for a new check runner. [R1](https://github.com/openai/codex/issues/15379) [R2](https://github.com/anthropics/claude-code/issues/62659) [R3](https://github.com/anthropics/claude-code/issues/10840)

### Cited Findings

#### R1 — Codex: subprocess trees surviving the agent's exit

- **Original report:** [openai/codex #15379, “Orphaned child processes persist after Codex parent exits”](https://github.com/openai/codex/issues/15379). Opened **2026-03-21**; original environment **codex-cli 0.116.0**, macOS M4, VS Code terminal. **Open** at access; last updated **2026-10-03**. The original trigger is a still-running long-lived command followed by normal or abrupt Codex exit. The reporter describes residual processes requiring manual cleanup. Its proposed waiter/reaper race is a **reporter hypothesis**, not an independently established cause. [R1](https://github.com/openai/codex/issues/15379)
- **Maintainer-side counterevidence:** `etraut-openai`, shown as `CONTRIBUTOR` by GitHub, asks for a version bisect and says, **“I think the behavior you're describing might be by design.”** The reporter withdraws the unsupported regression claim: survival was reproducible on 0.116.0, but the starting version and whether it was longstanding/by-design were unconfirmed. This is not a maintainer confirmation of a regression or a fix. [Response](https://github.com/openai/codex/issues/15379#issuecomment-4103401816) [Reporter correction](https://github.com/openai/codex/issues/15379#issuecomment-4103418299)
- **Later concrete workflow observation:** on **2026-10-03**, another participant reports **codex-cli 0.160.0, Ubuntu 24.04, `codex exec`**. An agent launched `node browser-review.mjs` using Playwright/headless Chromium through `exec_command`, received a session ID, then reached `task_complete` and exited. The reporter says the `codex-linux-sandbox → node → chrome-headless-shell` tree survived in **two runs**, for roughly **2 days 22 hours** and **2 days 8 hours**, until manually killed. This is a firsthand, versioned browser-check lifecycle report; public raw process captures and a minimal standalone reproducer are not attached in that comment. [Observation](https://github.com/openai/codex/issues/15379#issuecomment-5970813872)
- **Useful distinction, not runtime confirmation:** a **2026-09-06** participant audits pinned **0.153.4** source and explicitly says they **have not reproduced** a surviving native process on that release. They describe local termination returning without awaiting OS child exit, process-store draining before termination completion, and shutdown returning success after a worker timeout. Their conclusion is that an empty tracked-process list or successful termination result does not independently prove OS exit. We inspected the comment, **not the linked implementation**, so this remains attributed source analysis, not our code verification. [Analysis and limits](https://github.com/openai/codex/issues/15379#issuecomment-5563004612)
- **Actual resolution/workaround and evidence level:** manual cleanup is reported; no vendor-confirmed fix or fixed release appears in the inspected issue history. **Moderate evidence:** multiple firsthand, versioned observations and an explicit vendor-side qualification, but no independent reproduction here. Persistence deliberately permitted across an ordinary turn interruption must not be conflated with accidental survival after explicit shutdown. [R1](https://github.com/openai/codex/issues/15379)

#### R2 — Claude Code on Windows: “TaskStop succeeded” while Vite still serves

- **Original report:** [anthropics/claude-code #62659](https://github.com/anthropics/claude-code/issues/62659). Opened **2026-05-27**, **Claude Code 2.1.150**, Windows 11 **10.0.26200.8457**, Git Bash and PowerShell. The reporter supplies live Job Object membership/flag measurements and a controlled grandchild-inheritance experiment. They attribute surviving descendants to missing per-command kill-on-close containment for Bash and `SILENT_BREAKAWAY_OK` defeating inheritance for another path. These are **reporter measurements and causal analysis**, not a maintainer-endorsed root cause. [R2](https://github.com/anthropics/claude-code/issues/62659)
- **Direct local-development trigger:** a **2026-05-30** comment reports Windows 11, Claude Code **2.1.x**: start `pnpm dev` in a background Bash task, then invoke **TaskStop**. The tool returns **“Successfully stopped task”**, but **`localhost:3000` remains reachable**. The reporter identifies a listening `node`/Vite process whose parent shell has died. Explicit process termination associated with that port reportedly frees it. This is the clearest selected account of a service remaining alive after an agent's successful stop acknowledgement. The comment does not give an exact patch version or public raw trace. [Vite observation](https://github.com/anthropics/claude-code/issues/62659#issuecomment-4583776982)
- **Existing containment workaround is meaningful counterevidence:** a separate **2026-05-28** commenter reports wrapping headless Claude in a user-space **kill-on-close Job Object without silent breakaway**, and says MCP children/grandchildren then inherit containment and are reaped when its handle closes. That is a reported wrapper workaround for the **MCP spawn path**, not proof that the Vite/Bash case or every escaped descendant is fixed. It nevertheless argues against treating lifecycle containment as a capability that necessarily needs a new agent-specific service product. [Workaround and explicit open question](https://github.com/anthropics/claude-code/issues/62659#issuecomment-4567917620)
- **Actual vendor-repository disposition:** **closed `not_planned` on 2026-09-01**, by `github-actions[bot]`: **“Closing for now — inactive for too long.”** Last updated **2026-09-02**. The inspected thread contains no maintainer-confirmed implementation fix. **Closed does not mean resolved** here; equally, complaints after closure are not a reproduction on the latest release. [Closure](https://github.com/anthropics/claude-code/issues/62659#issuecomment-5492489472) [R2 status](https://github.com/anthropics/claude-code/issues/62659)
- **Evidence level and safety limit:** relatively strong **reporter-level** evidence: measured containment, a controlled experiment, and a distinct concrete Vite stop failure. No local reproduction or vendor-confirmed cause. Port-based killing is a historical workaround, **not a safe general recommendation**: a port alone does not establish ownership of the listener. [Original measurements](https://github.com/anthropics/claude-code/issues/62659) [Vite observation](https://github.com/anthropics/claude-code/issues/62659#issuecomment-4583776982)

#### R3 — Claude Code: dead server tasks still described as running

- **Original report:** [anthropics/claude-code #10840, “Stale background process reminders continue after process is killed”](https://github.com/anthropics/claude-code/issues/10840). Opened **2025-11-02**, **Claude Code 2.0.31**, Linux. Trigger: start a background Bash process, kill it through KillShell or allow it to terminate, then continue receiving reminders with `status: running`. The original report has reproduction steps but no attached logs and no version bisect for its regression claim. [R3](https://github.com/anthropics/claude-code/issues/10840)
- **Concrete corroboration:** a **2025-12-07** Windows commenter shows reminders for **seven `python run_server.py` tasks**. KillShell reportedly says six are already killed; OS inspection shows no Python processes and only one actual Bash child. The commenter associates the appearance of stale reminders with context compression. **The status contradiction is an observation; compression causing it, or sharing a root cause with another bug, is a hypothesis.** [Status/OS comparison](https://github.com/anthropics/claude-code/issues/10840#issuecomment-3623476841)
- **Actual disposition:** **closed `not_planned` on 2026-02-08** by an inactivity bot and later locked; labels include `duplicate` and `autoclose`. The closure says **“automatically closed due to 60 days of inactivity.”** Neither the duplicate label nor the closure demonstrates a shipped fix. No current-release reproduction or maintainer explanation appears in the selected thread. [Closure](https://github.com/anthropics/claude-code/issues/10840#issuecomment-3866890828) [R3 status](https://github.com/anthropics/claude-code/issues/10840)
- **Evidence level:** **moderate historical evidence** for stale task bookkeeping, weaker evidence for a current limitation, and **no confirmation of the context-compression cause**. The issue is useful precisely because it is the opposite mismatch from R2: tracked “running” with no process, versus tracked “stopped” with a live listener. [R3](https://github.com/anthropics/claude-code/issues/10840) [R2 Vite observation](https://github.com/anthropics/claude-code/issues/62659#issuecomment-4583776982)

### Inferences

- Treat **stop requested**, **root process exited**, **owned descendants exited**, and **owned endpoint released** as separate claims. A task ID or success string alone did not establish the last two in these observations. This is a contract/containment problem before it is an interface problem. [R1](https://github.com/openai/codex/issues/15379) [R2](https://github.com/anthropics/claude-code/issues/62659)
- A leftover Vite listener could cause a later port collision or wrong-instance verification, but **neither actually checking the wrong application revision nor a readiness race is demonstrated** by these selected reports. Do not promote that plausible causal chain to an observed incident. [R2 Vite observation](https://github.com/anthropics/claude-code/issues/62659#issuecomment-4583776982)
- Lifecycle state reconstructed from an agent transcript needs revalidation against the owning manager/OS; simply retaining a session or its last “running” text would preserve the R3 error. [R3](https://github.com/anthropics/claude-code/issues/10840)

### Gaps

- No well-founded primary report was established in this bounded corpus for **a browser verifying the wrong worktree/revision**, **browser/check network isolation causing a false pass**, or **readiness probing the wrong generation**. R1 concerns an orphaned browser check, not a false verification result.
- No maintainer-confirmed fixed release was established for these mechanisms. Two closures are housekeeping, not evidence of resolution; an open issue is not proof a current release still reproduces.
- None of these issue counts or selected observations establish prevalence, market size, willingness to adopt, runtime overhead, or aggregate token cost. No local trace was collected.

## 2. What does an established lifecycle alternative actually guarantee?

### Takeaway

**Docker Compose already supplies an agent-callable, ordinary CLI baseline** for declared services: managed background lifetime, attached shutdown, bounded running/health waits, configuration/image reconciliation, and selected check exit-code propagation. These are substantive existing behaviors, not merely named terminal sessions. Their documented scope is **Compose containers**, not arbitrary host-native processes or semantic proof that a browser saw the intended source revision. [B1](https://docs.docker.com/reference/cli/docker/compose/up/)

### Cited Findings

- **Selected baseline B1:** [official `docker compose up` reference](https://docs.docker.com/reference/cli/docker/compose/up/), live **unversioned** documentation accessed **2026-10-18**. CLI semantics were additionally checked through **Context7 `/docker/compose`**, whose results include the command reference and flag definitions. This was documentation verification, **not** verification of any installed Docker/Compose version or a local runtime test. [B1](https://docs.docker.com/reference/cli/docker/compose/up/)
- **Lifetime and shutdown:** the reference says attached `up` aggregates container output and **“When the command exits, all containers are stopped.”** `up --detach` instead starts containers in the background and leaves them running. It explicitly documents stopping containers on **SIGINT/SIGTERM**. Deliberately detached containers therefore are not, merely by surviving the launching agent, evidence of an orphan bug. The reference does not promise cleanup on an uncatchable CLI crash/SIGKILL. [B1](https://docs.docker.com/reference/cli/docker/compose/up/)
- **Bounded readiness:** `--wait` means **“Wait for services to be running|healthy. Implies detached mode.”** `--wait-timeout` bounds that wait in **seconds**. Thus a documented baseline invocation, **not executed here**, is `docker compose up --wait --wait-timeout 60`. “Running|healthy” is not an unconditional promise of application-level readiness or correct revision; a semantically useful health condition must be supplied by the project. [B1](https://docs.docker.com/reference/cli/docker/compose/up/)
- **Existing-instance reconciliation:** `up` stops/recreates existing service containers when their configuration or image has changed, preserving mounted volumes; `--force-recreate` forces recreation and `--no-recreate` disables it. This directly rebuts a straw baseline of “always reuse whatever happens to answer on the port.” It still does not document an end-to-end browser-to-source-generation receipt. [B1](https://docs.docker.com/reference/cli/docker/compose/up/)
- **Orphan scope:** `--remove-orphans` removes containers for services **not defined in the Compose file**. It does **not** mean “find and kill all orphaned host development processes.” `--timeout` is a **container shutdown timeout**, not a command-runtime or readiness timeout; do not interchange it with `--wait-timeout`. [B1](https://docs.docker.com/reference/cli/docker/compose/up/)
- **Finite checks can already propagate failure:** `--exit-code-from SERVICE` returns the selected service container's exit code and implies `--abort-on-container-exit`. The reference also documents `--abort-on-container-failure`; abort flags are incompatible with detached mode. For a project that already defines a finite check service, these are useful lifecycle/exit semantics without inventing retained-session check execution. They do not themselves prove the test asserted the right thing. [B1](https://docs.docker.com/reference/cli/docker/compose/up/)

### Inferences

- For **services actually launched under the manager**, separation of the manager's lifetime from the agent's shell plus explicit lifecycle operations can address the ownership gap exposed by R1/R2. A named agent session remains useful for interaction, but it is not the source of truth for process containment or successful cleanup. A manager cannot retroactively own an arbitrary unregistered host listener merely because an agent knows its port. [B1](https://docs.docker.com/reference/cli/docker/compose/up/) [R1](https://github.com/openai/codex/issues/15379) [R2](https://github.com/anthropics/claude-code/issues/62659)
- **Containerizing everything is not a free assumption.** Compose is a fair demonstrated baseline where services/checks are already containerized or the project accepts that boundary. For host-native workflows, compare against an ordinary manager with verified equivalent ownership/containment semantics; this research did not inspect a second manager and makes no claim that every native manager has them. No image/build/startup cost comparison is supported by this corpus. [B1 scope](https://docs.docker.com/reference/cli/docker/compose/up/)
- The strongest reported Windows workaround uses ordinary OS containment, not a new MCP capability. Its narrower demonstrated path should be tested before generalizing it to Bash, browsers, or other environments. [R2 workaround](https://github.com/anthropics/claude-code/issues/62659#issuecomment-4567917620)

### Gaps

- The one selected baseline page does not establish arbitrary host descendant containment, native worktree isolation, browser endpoint provenance, or a durable cross-agent handoff protocol. Absence from this page is **not proof that Compose or integrations cannot provide a solution**.
- No baseline was run, so these are documented semantics rather than an observed solution to the selected reports on the user's machines.

## 3. What increment, if any, should host-native proc-compose pursue?

### Takeaway

**No additional feature is justified yet.** The reports motivate correct ownership, confirmed teardown, and live-state revalidation; those requirements can fit existing agent tools plus an ordinary lifecycle manager and finite checks. They do not select retained-session managed check execution, a dashboard, or another MCP/SDK wrapper. [R1](https://github.com/openai/codex/issues/15379) [R2](https://github.com/anthropics/claude-code/issues/62659) [R3](https://github.com/anthropics/claude-code/issues/10840) [B1](https://docs.docker.com/reference/cli/docker/compose/up/)

### Cited Findings

- The concrete development-service failure is a **false successful stop with a surviving listener**, not inability to start a service or lack of a dashboard. [R2 Vite observation](https://github.com/anthropics/claude-code/issues/62659#issuecomment-4583776982)
- The browser-check report demonstrates **cleanup after the agent exits**, not that the check must be retained in a service session. The stale-reminder report demonstrates **bookkeeping divergence**, not that another registry will necessarily be authoritative. [R1 browser observation](https://github.com/openai/codex/issues/15379#issuecomment-5970813872) [R3](https://github.com/anthropics/claude-code/issues/10840)
- Existing documented lifecycle/readiness/exit-code controls and a reported OS-containment workaround supply real counterexamples to “agents need a new service manager to do this at all.” [B1](https://docs.docker.com/reference/cli/docker/compose/up/) [R2 workaround](https://github.com/anthropics/claude-code/issues/62659#issuecomment-4567917620)

### Inferences

- **Default decision: no new feature.** Establish the no-new-feature workflow first: existing named agent sessions; services owned by an ordinary manager; bounded readiness/check operations; fresh, identity-aware verification records; explicit manager-scoped cleanup and post-cleanup observation. If that succeeds, a wrapper is convenience, not an additional agent capability. [B1](https://docs.docker.com/reference/cli/docker/compose/up/) [R1](https://github.com/openai/codex/issues/15379) [R2](https://github.com/anthropics/claude-code/issues/62659)
- **Only a conditional capability gap is worth investigating:** if an otherwise adequate native baseline cannot enforce **owner/generation-bound process containment and endpoint identity across cancellation or handoff**, proc-compose could potentially provide that enforceable boundary. It must distinguish incomplete cleanup from success and avoid touching unrelated work. Merely naming these properties, caching a PID/port, returning a receipt, or exposing them over MCP is not the increment; the increment would be a demonstrated guarantee the baseline actually lacks. The selected sources do **not** establish that such a gap remains. [R1 completion-contract analysis](https://github.com/openai/codex/issues/15379#issuecomment-5563004612) [R2](https://github.com/anthropics/claude-code/issues/62659) [R3](https://github.com/anthropics/claude-code/issues/10840)
- **Retained-session managed checks remain unselected.** If a browser/check command leaks outside the service manager, first test ordinary scoped containment and a finite check with an explicit deadline/exit result. Adding a second lifecycle subsystem before that comparison would not follow from these observations. [R1 browser observation](https://github.com/openai/codex/issues/15379#issuecomment-5970813872) [B1 exit-code controls](https://docs.docker.com/reference/cli/docker/compose/up/)

### Gaps

**A small, falsifiable local workflow trace is still required; this is a proposed evaluation, not work performed or a feature approval:**

1. Capture one representative existing **edit → start/reuse → readiness → browser/check → stop → handoff** workflow, including actual agent/harness/manager versions, checkout/worktree, command results, process ownership, selected endpoint, and timestamps. Establish the no-new-feature baseline before proposing changes.
2. When authorized in a disposable environment, examine three bounded paths: normal completion; explicit cancellation/stop with a wrapper/grandchild; and handoff/resume with a pre-existing listener. Include an unrelated service as a negative control. Distinguish intentional service retention from unwanted survivors.
3. Observe the disputed boundaries directly: does a successful stop leave any owned process/listener; does resumed status agree with the manager/OS; does the browser/check reach the intended service generation rather than merely receive HTTP 200; and does a timeout yield an unambiguous check result? Record missing observations instead of substituting a session label or elapsed time.
4. Report **wall-clock elapsed time separately from cumulative concurrent command durations**, plus wrong-instance checks, unwanted survivors, unrelated-process interference, and manual recovery steps. There is no cost or performance estimate in this note.
5. **Stop condition:** if ordinary management plus finite checks and fresh verification meets those conditions, ship no new agent capability. If it fails, identify the smallest missing enforceable contract and show it fails on the baseline before selecting an implementation. Failure due only to unregistered services, inadequate health assertions, or incorrect endpoint selection may be workflow/configuration work rather than a product capability gap.
