# Official coding-agent constraints for multi-service local development

> **Historical background — 2026-10-18; relocated for publication on 2026-10-19.** Original wording and citation line labels are retained as historical evidence, not current pilot instructions or fresh verification. Use the [canonical pilot](../../reports/Agent%20workflow%20opportunities%20and%20validation.md#canonical-pilot) and the later municipal reports indexed in the [research README](../../README.md). Any `file://` citations are **local-only evidence**; their referenced files and raw artifacts are not published here.

## What do Codex and Claude Code officially supply for local execution and verification?

### Takeaway

The documented harnesses already supply asynchronous command execution, output retrieval, process termination, and ways to observe ongoing work; a missing generic “run a process” capability is not established. The consequential constraints are execution mode, ownership/lifetime, sandbox and network reachability, bounded output, and the distinction between a tool finishing and an application actually passing its checks. [Codex App Server](https://learn.chatgpt.com/docs/app-server.md); [Claude tools reference](https://code.claude.com/docs/en/tools-reference.md); [Claude sandboxing](https://code.claude.com/docs/en/sandboxing.md)

#### Codex: concrete supported surfaces and boundaries

- **App Server is an integration surface, not the necessary baseline for ordinary local work.** O1 says: “Use it when you want a deep integration inside your own product,” covering authentication, history, approvals, and streamed agent events. For jobs/CI, the page instead directs readers to the Codex SDK. This is vendor guidance about the intended surface, not a recommendation to put proc-compose behind another agent-specific API. **Section:** introduction. [O1](https://learn.chatgpt.com/docs/app-server.md)

- **Sandboxed commands already have timeout and continuation controls.** `command/exec` runs an argv command “under the server sandbox without creating a thread.” It accepts `cwd`, `sandboxPolicy`, and `timeoutMs`; omitted `timeoutMs` uses the server default, whose numeric value this page does not specify. It documents PTY mode with `tty: true`, a `processId` for follow-up `command/exec/write`, `/resize`, and `/terminate`, and `streamStdoutStderr: true` for `command/exec/outputDelta`. Its completion example includes `exitCode`, `stdout`, and `stderr`. **Section:** Command execution. [O1](https://learn.chatgpt.com/docs/app-server.md)

- **There is already an explicit process-control API, but it has a different trust boundary.** Exact quote: “`process/*` is an experimental, explicit process-control API.” It requires `capabilities.experimentalApi = true` and “runs outside Codex's sandbox.” `process/spawn` uses a caller-provided `processHandle`; output and completion arrive through `process/outputDelta` and `process/exited`; stdin, PTY resize, and termination use `process/writeStdin`, `process/resizePty`, and `process/kill`. The example runs `python3 -m pytest -q` and reports `exitCode: 0`. **Section:** Process execution. This establishes existing harness plumbing, not production suitability or stable-version availability. [O1](https://learn.chatgpt.com/docs/app-server.md)

- **Thread background terminals can already be inspected and stopped.** `thread/backgroundTerminals/list`, `/terminate`, and `/clean` are experimental and require the same opt-in. Listing applies to a loaded thread; the page explicitly says the returned `processId` is the **App Server process id**. The example separately includes nullable `osPid`, `cpuPercent`, and `rssKb`; it does not establish persistent OS identity or guaranteed resource measurements. **Section:** Clean background terminals. [O1](https://learn.chatgpt.com/docs/app-server.md)

- **User-entered shell commands are a separate, less restricted operation.** `thread/shellCommand` returns an immediate acknowledgement and streams progress. Exact quote: “This API runs outside the sandbox with full access and doesn't inherit the thread sandbox policy.” It is for explicit user-initiated commands. Its documented default timeout is **one hour**, with `0` meaning immediate timeout and negative values rejected. **Do not apply this one-hour default to model-generated commands or `command/exec`.** If a turn is already active, formatted command output is injected into that turn's message stream. **Section:** Run a thread shell command. [O1](https://learn.chatgpt.com/docs/app-server.md)

- **Sandbox policy belongs to the execution surface, not to the command's name.** O1 documents `readOnly`, `workspaceWrite`, `externalSandbox`, and `dangerFullAccess` policies, explicit readable-root controls, and `networkAccess`. In `externalSandbox`, network access is `restricted` by default or can be `enabled`; `workspaceWrite` uses a boolean. It says `externalSandbox` skips Codex's own enforcement when the server process is already sandboxed. A custom process wrapper must not be assumed to preserve these boundaries automatically. **Sections:** Sandbox read access; Command execution. [O1](https://learn.chatgpt.com/docs/app-server.md)

- **Conversation continuation and process lifetime are distinct documented concepts.** Threads contain turns and items; `thread/resume` continues stored history, `thread/fork` branches it, and `turn/steer` appends input to an active turn. `turn/interrupt` ends a turn with `status: "interrupted"`. Background cleanup has separate methods. **Sections:** Core primitives; Lifecycle overview; Start or resume a thread; Steer an active turn; Interrupt a turn. O1 does **not** thereby promise which background processes survive interruption, disconnect, server shutdown, or subsequent resume. [O1](https://learn.chatgpt.com/docs/app-server.md)

- **Verification evidence is exposed, but not interpreted as application correctness by the protocol.** A `commandExecution` item carries command, cwd, status, optional aggregated output, exit code, and duration; output deltas stream separately. Exact quote: “`item/completed` ... treat this as the authoritative state.” `turn/completed` can be completed, interrupted, or failed; `contextCompaction` is a separate item. Image input/viewing and web-search items are documented, but this page does not establish an interactive browser-testing setup. **Sections:** Events / Turn events / Items / Item deltas. [O1](https://learn.chatgpt.com/docs/app-server.md)

#### Claude Code: command mode, lifetime, output, and observation

- **Shell state is not a persistent interactive shell.** Exact quotes: “The Bash tool runs each command in a separate process” and “Environment variables don't persist. An `export` in one command won't be available in the next.” Main-session cwd changes can carry over inside project/additional directories; subagent cwd changes never carry over. Startup-file aliases/functions are captured and reapplied. The documented choices for durable environment setup are activation before launching Claude Code, `CLAUDE_ENV_FILE`, or a SessionStart hook. **Section:** Bash tool behavior / What persists between commands. [A1](https://code.claude.com/docs/en/tools-reference.md)

- **Foreground timeout is not necessarily process termination.** Foreground defaults are **2 minutes** (`BASH_DEFAULT_TIMEOUT_MS`) and an out-of-box **10-minute** ceiling (`BASH_MAX_TIMEOUT_MS`); the effective ceiling is the larger of these configured values. Exact quote: “When a foreground command reaches its timeout without finishing, Claude Code moves it to the background instead of stopping it, unless the command starts with `sleep`.” Bare mode or `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` disables that functionality, so timeout stops the command instead. A move reports the task ID and output-file path, and backgrounded `cd` does not change later commands' cwd. **Sections:** Timeout and output limits; Foreground commands that move to the background. [A1](https://code.claude.com/docs/en/tools-reference.md)

- **Dev-server/watch execution already has a documented simple path.** Exact quote: “For long-running processes such as dev servers or watch builds, Claude can set `run_in_background: true` ... and continue working while it runs.” `/tasks` lists/stops them; `TaskStop` stops by ID. `TaskOutput` was removed in **v2.1.277**; Claude now reads background output files using `Read`. This is stronger counterevidence to a missing generic background-process interface than an assertion about hypothetical future agent capability. **Sections:** Background commands; tools table. [A1](https://code.claude.com/docs/en/tools-reference.md)

- **Ownership matters more than “background” alone.** A foreground subagent's background command stops when that subagent ends, fails, or is interrupted. Commands started by the main conversation or a background subagent survive a final response until exit, explicit stop, or applicable time limit. A `-p` run stays open while a main-conversation background command runs; a background subagent's command is stopped when the run exits. **Section:** When a background command stops. These are different lifetimes; do not tell an agent merely to “background the stack” without naming who owns it. [A1](https://code.claude.com/docs/en/tools-reference.md)

- **Attended local and unattended modes now differ.** Exact quote: “A local session you work in from a terminal, the desktop app, or the VS Code extension has no time limit on background commands.” Unattended `-p`, SDK, CI, and cloud sessions have limits: normally **30 minutes**, or a requested background `timeout`, up to **2 hours**; a moved foreground command gets 30 minutes from the move. A single text-prompt `-p` run, unlike `--input-format stream-json`, has **10-minute** defaults. The limit requires **v2.1.285**; before **v2.1.288** it applied in every session. The documented environment variables can raise defaults/maxima, not lower those background limits. On expiry the harness stops the command and tells Claude why; it can restart with a longer timeout. **Sections:** Time limit for background commands; Raise the time limit. These numbers are documentation claims for the described versions/modes, not measured behavior here. [A1](https://code.claude.com/docs/en/tools-reference.md)

- **Output is bounded and can be lossy from the model's perspective.** A command exceeding **5 GB** output is killed. Default valid results are inline up to roughly **30,000 characters**; larger valid results provide a saved path and preview, with the saved result truncated past **64 MiB**. Failures get roughly **10,000-character** head-and-tail excerpts, without a file path. The read-back window defaults to 30,000 and is configurable up to 150,000; increasing it does not increase inline ceilings. This makes a concise application-generated result/receipt valuable independently of generic log streaming. **Section:** Output limits. [A1](https://code.claude.com/docs/en/tools-reference.md)

- **Reactive log/status observation is already supplied in some configurations.** `Monitor` can tail logs, track long-running script output, poll status, or consume a WebSocket feed while the conversation continues. Exact quote: “Every watch Claude starts has a deadline”: **5 minutes** by default, at most **30 minutes**, and at most **10 minutes** for single-prompt non-interactive `-p`. Commands use Bash permission rules. Availability excludes Amazon Bedrock, Google's Agent Platform, Microsoft Foundry, and specified telemetry-disabled configurations; Windows requires Git Bash. This is a finite, configuration-dependent watch, not a durable supervisor or an application-readiness oracle. **Section:** Monitor tool. [A1](https://code.claude.com/docs/en/tools-reference.md)

- **Local HTTP testing has an explicitly documented non-browser fallback.** Exact quote: “WebFetch refuses `localhost` and any other hostname without a dot.” Its error tells Claude to use **`curl` through Bash** for local servers. That establishes a simple local endpoint-check path, subject to shell sandbox policy; it does not establish JS execution, browser interaction, authentication-state handling, or an end-to-end browser assertion. **Section:** WebFetch tool behavior. [A1](https://code.claude.com/docs/en/tools-reference.md)

- **Subagent context is scoped.** The Agent tool uses a separate context window; the parent receives its final result, not intermediate tool calls/output. Forked subagents can inherit conversation history. This means logs and operational facts known to one subagent are not necessarily in the parent's working context. **Section:** Agent tool behavior. [A1](https://code.claude.com/docs/en/tools-reference.md)

#### Claude Code: sandbox/network details that affect multi-service local work

- **Sandboxing is optional and is not equivalent to permission mode.** Exact quotes: “The sandbox is off by default” and “The sandbox covers shell commands only.” When enabled, it covers Bash, PowerShell, Monitor, and their children on macOS/Linux/WSL2; native Windows commands are unsandboxed. File/web tools, hooks, local MCP servers, LSPs, plugin monitors, and helper commands are outside this shell sandbox. A2 distinguishes pre-execution permission decisions from OS-enforced restrictions during execution. **Sections:** introduction; What the sandbox restricts; What runs outside the sandbox; How sandboxing relates to permissions and permission modes. [A2](https://code.claude.com/docs/en/sandboxing.md)

- **The default sandbox is not secret isolation.** Writes are allowed to working/additional directories and a per-user temp directory, with protected paths denied. Reads include most of the machine, explicitly including credential files; environment variables are inherited, “including any secrets in its environment.” Credential protection/scrubbing is separately configurable. Therefore “the harness sandboxed it” is not evidence that a service or test was launched with a minimal environment. **Section:** What the sandbox restricts, default-access table. [A2](https://code.claude.com/docs/en/sandboxing.md)

- **Local naming and network namespaces can change reachability.** Sandboxed Linux/WSL2 commands use a separate network namespace with no direct network connection; traffic goes through a host proxy governed by allowed domains and permission mode. Allowed domains start empty. After hostname approval, the proxy refuses names resolving only to local addresses, but explicitly allows `localhost` and `*.localhost` to resolve to loopback; IP-literal decisions depend on domain policy and permission mode. This is not a promise that any custom local hostname, listening socket, or port will work unchanged. **Sections:** What the sandbox restricts; Network isolation; Hostnames that resolve to local addresses. [A2](https://code.claude.com/docs/en/sandboxing.md)

- **A sandbox failure can change the execution boundary, not just the error message.** By default unavailable sandbox dependencies/platform support lead to unsandboxed commands; `sandbox.failIfUnavailable: true` instead fails startup. Claude can retry blocked commands outside the sandbox unless configured otherwise; strict mode disables the retry, with separately documented exceptions/settings. Commands typed by a person using `!` are unsandboxed in most sessions. **Sections:** Get started; What runs outside the sandbox; The unsandboxed retry escape hatch; Turn off the retry with strict sandbox mode. This is why wrapper/MCP execution should not be assumed to be a safer interchangeable route. [A2](https://code.claude.com/docs/en/sandboxing.md)

- **There are concrete vendor-recommended boundary checks.** A2 tells the user to ask Claude—not type the `!` commands themselves—to run `touch ~/sandbox-probe` and `curl --noproxy '*' https://example.com`, expecting write/network failures, and to decline an unsandboxed retry. These check the sandbox boundary, **not application functionality**. No such commands were run for this research. **Section:** Confirm commands run inside the sandbox. [A2](https://code.claude.com/docs/en/sandboxing.md)

### Inferences

- **A working loop need not introduce a new API:** run existing stack commands, use the harness's supported background path if the command remains attached, read bounded status/logs or output files, run existing application checks (including Bash `curl` for local HTTP), inspect the real completion/exit evidence, and explicitly stop task-owned work. This combines already documented mechanisms; it is not a claim that the model always executes the loop correctly. [O1](https://learn.chatgpt.com/docs/app-server.md); [A1](https://code.claude.com/docs/en/tools-reference.md)
- **For proc-compose specifically, avoid layering lifetimes accidentally.** A long-lived stack started under a foreground subagent is vulnerable to that subagent's documented lifetime; changing from an attended CLI to unattended/bare mode also changes timeout/background semantics. Prefer an explicitly identified owner and inspect the existing proc-compose session after any interruption rather than assuming tool return, final answer, or resumed history describes current process state. [A1](https://code.claude.com/docs/en/tools-reference.md); [O1](https://learn.chatgpt.com/docs/app-server.md)
- **Reachability must be tested from the actual execution boundary.** The browser, agent web-fetch tool, shell command, and local service are not interchangeable network contexts. In particular, an agent failing to fetch `localhost` is not evidence that the service is unhealthy or that proc-compose needs a new API. [A1](https://code.claude.com/docs/en/tools-reference.md); [A2](https://code.claude.com/docs/en/sandboxing.md)

### Gaps

- **No runtime/vendor-release validation:** no installed CLI versions or October release tags were checked. These notes establish what the live official pages said on the access date, not when every behavior shipped or whether deployments match the pages.
- **Codex CLI parity and cleanup guarantees:** O1 documents App Server, not the full model-facing CLI shell-tool schema. The selected evidence does not establish its numerical default timeout, exact timeout-to-continuation behavior, background-terminal survival on interrupt/disconnect/exit, reconnectable process handles, or descendant cleanup guarantees. Do not generalize `thread/shellCommand`'s one-hour default. Context7's broad interruption/cleanup summary was not accepted as proof of those missing guarantees.
- **Claude exit/interruption and main-session context:** A1 establishes subagent ownership and unattended-run lifetime, but these selected pages do not fully specify main-session interrupt/exit descendant cleanup or conversation compaction/resume behavior. Process persistence must not be inferred from conversation persistence.
- **Browser verification:** within the three-source budget, no complete Codex or Claude browser-driver installation/permission/local-origin workflow was established. Browser-based acceptance remains an application/tooling setup requirement, not a capability proved by image input, WebFetch, or shell execution.
- **Local socket semantics:** exact cross-sandbox listener binding, custom hostname, Unix-socket, proxy, and port behavior depends on configured environment/platform. No real topology was exercised; the docs do not validate this repository's particular multi-service networking.

## Which responsibilities belong to the agent harness, the supervisor, and application tests?

### Takeaway

The harness supplies tool execution, conversation/context plumbing, output transport, and configured permission/sandbox enforcement. It does not turn those transport/lifecycle facts into service readiness, an isolated test fixture, a transaction-safe check, or proof that the intended application behavior passed. [O1](https://learn.chatgpt.com/docs/app-server.md); [A1](https://code.claude.com/docs/en/tools-reference.md); [A2](https://code.claude.com/docs/en/sandboxing.md)

### Cited Findings

### Inferences

- **Supervisor-owned semantics remain distinct:** the coordinator-supplied proc-compose reuse baseline is named sessions/ports/resources, structured bounded logs/status/why, fresh-stack verify with cleanup receipts/environment reports, generation-aware restart wait, and an offline agent guide. Those capabilities are not equivalent to a harness's command ID or conversation thread; none is treated here as a newly discovered gap. The vendor documents establish process/conversation mechanisms rather than those application-stack semantics. [O1](https://learn.chatgpt.com/docs/app-server.md); [A1](https://code.claude.com/docs/en/tools-reference.md)
- **Application tests own the oracle and state safety:** HTTP/business assertions, browser flows, fixtures, database effects, auth context, and concurrent mutations are not proven by a zero exit code unless the chosen checks actually encode them. The Codex `pytest` example demonstrates running a check, not defining its correctness; Claude's `curl` fallback demonstrates reachability tooling, not end-to-end validation. These are analytical limits of the evidence, not claims that agents cannot write tests. [O1](https://learn.chatgpt.com/docs/app-server.md); [A1](https://code.claude.com/docs/en/tools-reference.md)
- **Finite observation is not supervision:** a Monitor deadline or agent output truncation is a harness constraint; it is not a reason to duplicate durable proc-compose logging or assume the service should stop when observation ends. Conversely, a background command surviving a final response is not evidence the stack is ready or safe to retain. [A1](https://code.claude.com/docs/en/tools-reference.md)
- **Verification should distinguish evidence levels:** (1) tool accepted/started, (2) process still alive or exited, (3) service readiness observed, (4) intended application assertions passed, (5) task-owned resources cleaned up. Only the first two are directly supplied by the documented process interfaces; the others need the supervisor/application's own checks and receipts. This is a proposed evidence discipline inferred from the protocol/lifecycle distinctions, not a claimed vendor-mandated test ladder. [O1](https://learn.chatgpt.com/docs/app-server.md); [A1](https://code.claude.com/docs/en/tools-reference.md)

### Gaps

- The selected documentation contains no proc-compose-specific integration, representative local multi-service benchmark, or evidence that its existing command contracts are insufficient.
- No guarantee was found in these selected pages that an agent always waits for all relevant test results, chooses the right assertions, inspects truncated logs, or cleans up every owned descendant. Availability of the mechanisms is not an observed reliability result.
- Application mutation/isolation policy, ownership across multiple local users/agents, and how resumed conversations rediscover the correct existing proc-compose session require repository/workload evidence, not an inference from vendor capability lists.

## Do the docs establish marginal benefit for another process API over proc-compose plus shell?

### Takeaway

**No demonstrated need for another generic process API follows from these docs.** The strongest counterevidence is that Claude explicitly supports background dev servers/watch builds and local Bash `curl`, while Codex already documents process-control and background-terminal APIs. Given the supplied proc-compose baseline, the next useful evidence is a reproducible command-contract failure in an actual local workflow—not another wrapper by default. [A1](https://code.claude.com/docs/en/tools-reference.md); [O1](https://learn.chatgpt.com/docs/app-server.md)

### Cited Findings

- **Most direct counterevidence:** Claude's Background commands section explicitly names “dev servers or watch builds,” `run_in_background: true`, and `/tasks`; its WebFetch section explicitly directs local-server requests to Bash `curl`. Ordinary command execution plus documented task management is therefore an official supported path, not merely an unsupported workaround. [A1](https://code.claude.com/docs/en/tools-reference.md)
- **Already-existing lower-level API:** Codex App Server documents `command/exec`, explicit experimental `process/*`, and experimental thread background-terminal list/terminate/clean. O1's introduction positions App Server for deep integration. The evidence supports reusing these only where that integration is actually needed; it does not establish that proc-compose should expose a parallel API. [O1](https://learn.chatgpt.com/docs/app-server.md)
- **A new route has a safety cost to account for:** Codex explicit process control is unsandboxed, and Claude local MCP servers/hooks run outside its Bash sandbox. API novelty can therefore change trust boundaries rather than simply improve ergonomics. [O1](https://learn.chatgpt.com/docs/app-server.md); [A2](https://code.claude.com/docs/en/sandboxing.md)

### Inferences

- **Smallest justified outcome now:** use the existing proc-compose agent guide/commands and document the harness-specific invocation, owner, output-retrieval, local-network, and stop semantics if a real use case needs clarification. Do not build an API merely to add start/status/logs/stop that the supplied baseline and harness already expose. This is a scope recommendation, not a measured productivity claim. [O1](https://learn.chatgpt.com/docs/app-server.md); [A1](https://code.claude.com/docs/en/tools-reference.md)
- **Possible need, explicitly unvalidated:** a durable receipt tied to a particular live stack/generation, safe sharing across agent sessions, or an application-specific check contract might matter in a real task. These are examples of evidence to look for, **not findings that proc-compose lacks them**. The coordinator's candidate “managed checks against an already-running session” remains unvalidated; no cited vendor page establishes demand for it. [O1](https://learn.chatgpt.com/docs/app-server.md); [A1](https://code.claude.com/docs/en/tools-reference.md)
- **Falsifiable follow-up pilot, not executed:** choose one existing representative multi-service development task and use only proc-compose's current commands plus supported shell tools. Record the exact CLI/version/mode, starting session/generation, command completion evidence, application check results, and cleanup receipt. Include three bounded perturbations: (a) a local endpoint blocked by the actual sandbox/network boundary, (b) a service restart before checking the result, and (c) an agent interruption followed by inspection of retained/terminated resources. These target the documented policy, ownership, and observation distinctions. [A1](https://code.claude.com/docs/en/tools-reference.md); [A2](https://code.claude.com/docs/en/sandboxing.md); [O1](https://learn.chatgpt.com/docs/app-server.md)
- **Pilot decision rule:** reject an extra API if existing commands produce correct, bounded, attributable results and cleanup in those cases. Consider only the narrowest contract change if a repeated failure cannot be fixed by the documented command/mode or existing proc-compose output; record the failure before choosing a feature. No speed ranking is offered: there are no representative timings here, and future measurements must separate concurrent command durations from end-to-end wall time. This is a proposed research criterion, not vendor evidence or a performance claim.
- **Rejected alternative:** treating generic agent autonomy/backgrounding announcements as evidence of product demand. The concrete docs instead establish mechanisms and caveats. Existing shell/harness facilities are the reuse baseline; none was rejected after a runtime comparison because no such comparison was authorized. [O1](https://learn.chatgpt.com/docs/app-server.md); [A1](https://code.claude.com/docs/en/tools-reference.md)

### Gaps

- No local-agent traces or workload timings were collected, so there is no quantified speed/productivity claim, causal optimization ranking, or observed failure rate.
- No evidence establishes how often proc-compose users need checks against an already-running stack, whether its existing commands already solve those cases, or whether a guide/example would suffice.
- The three-source budget prioritizes operational references over full browser and main-session UI guides. Exact installed-version compatibility, interrupt/exit cleanup, cross-session process recovery, and complete browser workflows remain the major verification uncertainties—not proof of a missing proc-compose feature.
