#### Additional verified positives that strengthen the competing-tools case

- **MCP has concrete documented utility beyond merely existing.** PM describes user-defined tools with typed arguments and parameterless resources, repeated invocation after completion, exit codes returned to clients, configurable global/per-process timeouts, and only one invocation running at a time per process with others queued. Its tools can coexist with regular processes and respect dependencies. These are documented operating affordances, not measured usability gains or proof of check-level cleanup. [PM, “Defining MCP Processes,” “Timeout Configuration,” “Behavior and Lifecycle”][PM]
- **Bounded diagnostics are not wholly missing from process-compose.** PM documents a one-shot log tail (default 100 lines), bounded log search (`top_k` maximum 100, `log_limit` maximum 5,000), a 50,000-line total-work cap with `"truncated": true`, and MCP result limits from per-process `log_length`. These are not byte ceilings or stable cursor/loss semantics; P-only “not established” remains an honest sample limit, not evidence of absence. [PM, “Built-in Control Tools,” “Limitations”][PM]
- **Devenv even documents descendant-exit verification for some adapters.** E1 “Manager adapters” defines `process-scope` as terminating the recorded OS process scope and verifying manager/descendant exit; its table assigns this adapter to external process-compose, honcho, hivemind and mprocs. This must not be generalized into verified behavior for every native-manager or crash path, but it prevents an unsupported blanket claim that competitors never document descendant verification. No such blanket claim appears in the reviewed research. [E1]
- **Compose offers retained and bounded-startup modes, not only fresh one-offs.** D1 lists `exec` for commands in a running container. DU documents detached retention and `--wait`/`--wait-timeout`; `--wait` waits for running/healthy and implies detached mode. `--exit-code-from` instead implies `--abort-on-container-exit`, which is incompatible with `-d`. Do not combine these into a fictitious single mode guaranteeing retained services plus stop-all check ownership. [D1]; [DU]
- **Tilt already integrates native build→run→readiness and edit-driven updates.** Its `serve_cmd` is persistent; successful build gates replacement, probes can gate initial dependent resources, and file dependencies can trigger updates. This is a stronger counterexample to an unmet generic native development-loop need than “Tilt supports local commands” alone. No measured correctness or performance equivalence follows. [T, `local_resource`][T]; [TL]

### Inferences

- The most adverse evidence is **overlap inside the proposed native niche**, not a discovery that a cited product lacks a feature. P, T and E1 all cover native orchestration; PM covers repeated agent-invoked tools. A native-process target can be sensible while an underserved segment remains unproven. [P]; [T]; [PM]; [E1]
- Substitutes and complements are **job-dependent**, not mutually exclusive product categories. A project can retain Compose infrastructure, devenv provisioning or Tilt integration while using another component. The report's explicit two-role descriptions and warning about duplicate lifecycle owners already prevent the obvious conflation. [D1]; [T]; [E1]

### Gaps

No external binary/release was installed or tested; no feature release introductions beyond displayed documentation labels were established. These sources do not establish installed client compatibility, cleanup under interruption/escape, authentication enforcement in practice, full worktree/data isolation, comparative maintenance cost, demand, or performance. No absence-of-product inference should be made from this bounded sample. [P]; [D1]; [D2]; [T]; [E1]; [E2]; [PM]

#### F1 — Medium: MCP's relative cost rank depends on a design that was not specified

- **Exact research locations:** `research/reports/Agent workflow opportunities and validation.md:51–61`; `research/research_notes/Agent workflow opportunities and validation/alternatives-and-opportunities.md:45–58`, especially :52 (“Medium / low / high”), :56 (transport/access-control burden), :58 (“always-on agent server”).
- **Source URL / heading / passage:** <https://f1bonacc1.github.io/process-compose/mcp-server/> — “SSE Transport Security”: “The `stdio` transport is not network-reachable and is unaffected.” “Enabling the MCP Server”: controls default false and server starts only with exposed processes or enabled controls. “Built-in Control Tools”: controls provide “full process-management access to the running project.”
- **Claim/evidence mismatch:** The source supports *real compatibility and authority concerns*, especially for SSE/network access and destructive controls. It does not establish the report's relative **high** ongoing cost against retained checks, contract changes or CLI guidance. An MCP surface need not entail an always-listening network server. The study already says these are qualitative judgments, not measured estimates: this is **not a false measured-cost claim**, but a design-sensitive ordering the evidence cannot verify. [PM]; [R:51–61](../../reports/Agent%20workflow%20opportunities%20and%20validation.md)
- **Corrected wording:** “Defer MCP because this study establishes no target-client requirement or measured usability advantage. Implementation and ongoing cost are unknown until transport, authority scope and contract reuse are specified; stdio avoids a network listener, whereas SSE adds listener and network-access safeguards. Both still require deliberate mutation authority and compatibility policy.” [PM]
- **Decision impact:** Keep the demand gate; do not use an unsupported fixed cost rank or a network-only architecture to rule out a small client-driven adapter. This changes the confidence/rationale of deferral, not authorization to implement.
- **Confidence:** **High** in the transport distinction and lack of comparative cost measurements in R/A; **low** in any prediction that an actual proc-compose adapter would be cheap or useful.
- **Strongest counterargument:** Even stdio adds a supported protocol, schemas, client/version behavior and another way to exercise destructive authority; it is not automatically a thin or safe wrapper. The report acknowledges qualitative uncertainty and permits measured-usability/client escalation. Its present **defer** decision remains defensible. [PM]; [R:51,61](../../reports/Agent%20workflow%20opportunities%20and%20validation.md); [A:52–56](../Agent%20workflow%20opportunities%20and%20validation/alternatives-and-opportunities.md)

#### F2 — Low: Tilt's serial-execution and deadline statements compress distinct scopes

- **Exact research locations:** `research/reports/Agent workflow opportunities and validation.md:44`; `research/research_notes/Agent workflow opportunities and validation/alternatives-and-opportunities.md:19`.
- **Source URL / heading / passage:** <https://docs.tilt.dev/local_resource.html> — “Parallelism”: “Tilt will run local resource **build commands** in serial with other commands”; “serve_cmd”: permits a “persistent process.” <https://docs.tilt.dev/api.html> — `ci_settings`: “Configures ‘tilt ci’ mode.”

The report makes neither implication explicitly; this is a precision improvement, not evidence of broken Tilt support. [T]; [TL]
- **Corrected wording:** “Tilt serializes local-resource build/update commands by default to avoid filesystem races (`allow_parallel=True` opts in); persistent `serve_cmd` processes are a separate lifecycle. `ci_settings` supplies pipeline/readiness deadlines for `tilt ci`.” [T]; [TL]
- **Decision impact:** Avoid understating Tilt's fitness for retained multi-server native development or overstating its general timeout contract. Its documented overlap remains strong.
- **Confidence:** **High** in the documentation scope; no runtime concurrency/cleanup result was established.
- **Strongest counterargument:** A:19 names `ci_settings`, and R:38 says these are documented semantics. A careful reader can already avoid the overbroad inference. This is **low severity**, not a reason to reject the comparison. [R:38,44](../../reports/Agent%20workflow%20opportunities%20and%20validation.md); [A:19](../Agent%20workflow%20opportunities%20and%20validation/alternatives-and-opportunities.md)

#### F3 — Low: devenv caches outputs/skips execution; its status predicate is not itself described as cached

- **Exact research locations:** `research/reports/Agent workflow opportunities and validation.md:45` (“cached checks”); `research/research_notes/Agent workflow opportunities and validation/alternatives-and-opportunities.md:20` (“cached status checks”).
- **Source URL / heading / passage:** <https://devenv.sh/tasks/> — “Avoiding running expensive `exec` via `status` check”: status “will be executed first” and a zero result skips `exec`; “the output from the most recent successful run will be restored.” “Executing tasks only when files have been modified” additionally documents mtime/content-hash-based skipping and preserved outputs.
- **Claim/evidence mismatch:** “Cached status checks” can imply the predicate is cached or that a successful task status means a newly executed verification. The documented contract is conditional task execution and cached output restoration. The report already warns about loaded-code identity and never explicitly claims cached success is a fresh assertion, so a high-severity false-pass accusation would be unsupported. [E2]; [R:30,45](../../reports/Agent%20workflow%20opportunities%20and%20validation.md)
- **Corrected wording:** “devenv tasks can run a status predicate before execution, skip `exec` on success, or skip unchanged file-dependent work; skipped tasks can restore prior successful JSON outputs. This is configurable reuse, not by itself a fresh check receipt.” [E2]
- **Decision impact:** Count caching as a reuse/efficiency affordance, not verification-freshness parity. No speed advantage was measured, and no runtime false pass was observed.
- **Confidence:** **High** in the documented distinction; installed-version behavior remains untested.
- **Strongest counterargument:** “Cached checks” is defensible shorthand for optional task reuse, and the study explicitly disclaims runtime guarantees and reproducibility-as-loaded-code proof. The correction is useful mainly when a synthesis compresses the caveats away. [A:20,62,75](../Agent%20workflow%20opportunities%20and%20validation/alternatives-and-opportunities.md); [R:38,45,93](../../reports/Agent%20workflow%20opportunities%20and%20validation.md)

## 3. What is the strongest case against CLI-first/no-feature, and does it change the recommendation?

### Takeaway

The strongest opposing case is **client-specific utility, not MCP novelty**: an incumbent already documents typed discovery, repeated on-demand commands, timeouts and queued execution alongside native services, with a stdio option that does not add a network listener. That makes a client-facing adapter plausible even when ordinary shell execution is technically possible. It still does not supply the missing user need or measured advantage required to authorize a feature. [PM]

### Cited Findings

- **A real alternative to recipe-only discovery exists.** PM lets clients enumerate named process tools/resources with descriptions/typed arguments, invoke them repeatedly and receive exits/output after execution. Its default controls can remain off. This is a concrete interface mechanism, not proof that a particular user can operate without shell tooling or needs an MCP migration. [PM, “MCP Tools,” “MCP Resources,” “Process State,” “Built-in Control Tools”][PM]
- **The competitor exposes more than universal shell commands over a fashionable transport.** PM documents invocation queuing per process and global/per-process deadlines, while tools can use dependencies and coexist with resident services. These are plausible affordances for repeated agent checks. No documented receipt proves build freshness, independent per-check descendant cleanup, required-service monitoring or interruption safety equivalent to proc-compose. [PM, “Timeout Configuration,” “Queued Execution,” “Integration with Regular Processes”][PM]
- **Native lifecycle integration is not a unique opening.** Tilt's build/update graph already integrates persistent local servers and native test commands; devenv offers task/process DAGs, ports and lifecycle selection; process-compose is explicitly a dependency-light native orchestrator. Any stronger product claim must identify a particular contract/client boundary, not merely the existence of multi-process native development. [P]; [T]; [TL]; [E1]; [E2]
- **A comparison of disposable and retained semantics is necessary, not sufficient.** DU's detached readiness versus abort/exit-code modes and E2's task-run stop versus retained `up` demonstrate that different execution modes already make different lifecycle tradeoffs. A new interface may have utility at a missing combination of ownership/evidence boundaries, but neither feature lists nor the current research establish demand for that combination. [DU]; [E2]

### Inferences

**Steelman against the recommendation:** “A CLI recipe can explain an interface without fixing client discovery, argument construction, policy scoping or tool-result handling. If a selected agent client demonstrably performs better with a bounded typed adapter over the *existing* proc-compose contract, insisting on CLI-only operation could preserve avoidable friction. Competitor MCP demonstrates feasibility and parity, not futility.” This is an inference from PM's documented mechanisms, **not a measured result**. The strongest counterargument is that the reviewed study already permits a measured usability failure—not just total lack of shell access—to reopen MCP. [PM]; [R:61](../../reports/Agent%20workflow%20opportunities%20and%20validation.md); [A:52](../Agent%20workflow%20opportunities%20and%20validation/alternatives-and-opportunities.md)

**Decision after adversarial review:**

1. **Retain the conditional no-feature / reuse-first pilot recommendation.** The sources do not disprove it, and feature overlap strengthens the case against implementing another generic runner. Treat it as an evidence-conserving next experiment, not proof that CLI-only is the optimal product endpoint. [P]; [D1]; [T]; [E1]; [E2]
2. **Make the MCP deferral rationale demand/client-driven, not novelty-driven or a fixed “high cost” fact.** Keep distinct alternatives: CLI guidance, an existing native supervisor, a transport adapter reusing the same contracts, and a new lifecycle feature. These have different scopes and must not inherit one another's costs or benefits. [PM]; [T]; [E1]; [E2]
3. **Do not certify the native niche.** Existing host toolchains and worktree iteration define a target to investigate; they do not demonstrate incumbent failure, willingness to migrate or better outcomes. “Dependable” needs equal boundary tests across alternatives before it becomes a comparative selling point. [P]; [T]; [E1]; [R:47](../../reports/Agent%20workflow%20opportunities%20and%20validation.md)
4. **A small falsifiable client test, if separately approved, could change the ordering.** Name one actual client/task, pin versions and compare current CLI guidance with its supported interface while holding lifecycle, assertions, authority, endpoints and cleanup constant. Record discovery/argument/result-handling failures, interventions and complete elapsed time; equal or worse outcomes reject the interface benefit. This is only a proposed discriminator, not an implemented pilot or an authorization to build an adapter. PM's existence supplies the mechanism to examine, not its effect size. [PM]

**Rejected reuse:** none of Compose, Tilt, devenv or process-compose was shown inadequate for its documented job. A new generic task language, parallel runner or duplicate lifecycle owner is not justified by these sources. Conversely, MCP was **not rejected as useless**: its novelty, client need, transport exposure and comparative maintenance cost are separate questions. [D1]; [T]; [E1]; [E2]; [PM]

### Gaps

Source coverage is **6/6 exact originals plus 3 minimal official clarifications**, with Context7 supplementation for all four tools. No inaccessible-original substitution was needed. Scope excludes proc-compose code correctness, agent/browser vendor documentation, a fresh landscape scan, user interviews, binary/release tests, empirical cost estimates and performance/demand measurement. The result is therefore **documentary verification and decision critique**, not a runtime certification or evidence that any candidate feature has zero utility.
