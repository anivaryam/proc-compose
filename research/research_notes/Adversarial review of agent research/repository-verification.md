# Adversarial repository verification of agent research

## 1. Which local capability claims need correction or qualification?

### Takeaway

**The source supports the study's reuse-first direction, but not every unqualified contract statement.** Three material qualifications concern parser-error JSON, Windows cross-session refusal, and incomplete retained `why` reconstruction. None establishes demand for another API or reverses the recommendation to validate existing integration first. This is a static audit, not runtime certification.

Research locations below refer to:

- **R** = `research/reports/Agent workflow opportunities and validation.md` ([report](../../reports/Agent%20workflow%20opportunities%20and%20validation.md)).
- **B** = `research/research_notes/Agent workflow opportunities and validation/proc-compose-baseline.md` ([baseline](../Agent%20workflow%20opportunities%20and%20validation/proc-compose-baseline.md)).
- **I** = `research/README.md` ([index](../../README.md)).

### Cited Findings

#### F1 — Medium: `verify --json` is not a universal JSON error contract

- **Research location / claim:** `research/reports/Agent workflow opportunities and validation.md:20`: “`verify --json` emits one bounded object; other failed commands can emit stderr only.” B:21 also summarizes its JSON/exit surface without the parser exception.
- **Primary counterevidence:** [`cmd/proc-compose/verify.go:311–318`](../../../cmd/proc-compose/verify.go#L311-L318) installs a flag-error handler that writes plain stderr and returns usage exit 2, without calling the JSON renderer. The existing test expressly passes `verify --json --bogus -- true` and expects **empty stdout**, stderr containing `unknown flag`, and exit 2 ([`cmd/proc-compose/verify_cli_test.go:109–112`](../../../cmd/proc-compose/verify_cli_test.go#L109-L112)). This exception applies even with `--json` before the bad flag; the help's “before … recognised” wording is narrower than that test ([`cmd/proc-compose/verify.go:87–92`](../../../cmd/proc-compose/verify.go#L87-L92)). Test source inspected, not executed.
- **Corrected formulation:** Once argument parsing reaches the operation, normal results and semantic refusals use one bounded `verify.response` or compact error; **flag-parsing failures can produce no JSON**, so clients must handle nonzero exit plus empty/non-JSON stdout. Encoding/output errors are also not successful JSON delivery ([renderer:157–176](../../../cmd/proc-compose/verify.go#L157-L176); [encoder:393–416](../../../internal/verify/result.go#L393-L416)).
- **Decision effect:** Include this exception in the existing-CLI recipe and parsing acceptance cases. It weakens the suggestion that only non-verify commands need a text-error fallback, not the reuse-first recommendation. No new transport is implied.
- **Confidence:** High, direct control flow plus an explicit existing assertion. **Strongest counterargument:** Correct, supported invocations do receive the promised object, and the embedded guide mentions parser exceptions. This is a missing research qualification rather than evidence that successful verify output is malformed.

#### F2 — Medium: default cross-session refusal has a narrower Windows boundary

- **Research location / claim:** `research/reports/Agent workflow opportunities and validation.md:30` and `research/research_notes/Agent workflow opportunities and validation/proc-compose-baseline.md:49` say Linux/Windows attribute sockets, macOS cannot, and fresh verify rejects answers from another live session by default. The macOS caveat is present; Windows' leased-port-only limitation is not.
- **Primary counterevidence:** Windows can identify a foreign socket holder, but [`internal/runner/processgroup_windows.go:308–312`](../../../internal/runner/processgroup_windows.go#L308-L312) deliberately never maps that holder to another session's recorded group. Session placement falls back to declared port assignments and otherwise returns `outside_session` ([`internal/runner/attest.go:264–299`](../../../internal/runner/attest.go#L264-L299)); default refusal rejects only `foreign` plus `cross_session`, not every foreign holder ([same file:316–330](../../../internal/runner/attest.go#L316-L330)). The product documentation explicitly says **Windows refuses only a port the other session leases** ([`docs/verify.md:47–59`](../../../docs/verify.md#L47-L59)).
- **Counterexample / corrected formulation:** On Windows, another live session's service on an undeclared/hardcoded port can be attributed `foreign` yet placed `outside_session`, and its passing probe can count under default verify. Say: default verify refuses **attributed answers placed in another positively live session in the discoverable runtime registry**; Linux can use proven recorded-group membership or a leased port, Windows only a leased port, and macOS does not attribute/refuse. `foreign_listener: reject` widens refusal to identified foreign holders, but still accepts unattributable answers ([policy:321–330](../../../internal/runner/attest.go#L321-L330); [macOS backend](../../../internal/runner/attest_other.go#L11-L16); [registry:48–73](../../../internal/registry/registry.go#L48-L73)).
- **Decision effect:** Do not describe the proposed wrong-worktree gate as a platform-independent built-in guarantee. Declare named ports and application readback expectations; test the intended platform. This strengthens the existing identity caution, not the case for a universal attestation feature.
- **Confidence:** High for static behavior; Windows was not executed. **Strongest counterargument:** The study already allows `outside_session`/unattributable answers and cites documentation containing the limit. The omission is material shorthand, not a contradiction of its central “readiness is not identity” warning.

#### F3 — Medium: retained `why` can lose incomplete-state-history evidence

- **Research location / claim:** `research/reports/Agent workflow opportunities and validation.md:16,28` and `research/research_notes/Agent workflow opportunities and validation/proc-compose-baseline.md:20` present explicit gaps/truncation alongside live/retained `why`, recommending finite failure packets with truncation evidence.
- **Primary counterevidence:** Retained `why PROCESS` reconstructs state from the last **1000 state events / 1 MiB**, but copies only `page.Events`; it discards that reconstruction page's `Gap` and `Truncated` ([`cmd/proc-compose/why.go:71–90`](../../../cmd/proc-compose/why.go#L71-L90)). A dependency missing from the reconstructed map is silently omitted from `blocked_by` ([same file:100–115](../../../cmd/proc-compose/why.go#L100-L115)). The returned `context` is a **different**, process-filtered 20-event / 16-KiB query ([same file:116–125](../../../cmd/proc-compose/why.go#L116-L125)); its flags do not certify the state reconstruction.
- **Source-traced counterexample, not executed:** An old unready dependency state, more than 1000 intervening state transitions for another process, then a recent dependent's failed state leaves the dependent available but the dependency absent. `blocked_by` can be empty while the small selected-process context is untruncated. The internal tail query would flag its own omissions, but that flag is not propagated ([`internal/logs/query.go:115–130`](../../../internal/logs/query.go#L115-L130)). The existing retained-why test covers only two states, not this boundary ([`cmd/proc-compose/helpers_test.go:69–103`](../../../cmd/proc-compose/helpers_test.go#L69-L103)).
- **Corrected formulation:** `logs` pages expose their own gaps/truncation, and `why` labels live versus historical evidence; **an empty retained `blocked_by` or clear context flags do not establish complete retained state evidence**. Also, bounded context event bytes are not a universal byte cap for the whole `why` object: project/process/dependency fields are serialized separately ([packet shape:16–23](../../../cmd/proc-compose/why.go#L16-L23)). `why --attempt` is a different path with its own scan/history limits, not the same reconstruction algorithm ([`internal/verify/diagnose.go:111–138,149–170`](../../../internal/verify/diagnose.go#L111-L138)).
- **Decision effect:** Qualify diagnostic completeness before marketing dependable handoff evidence; retain direct cursor pages when completeness matters. This is a concrete existing-contract boundary worth a later separately authorized regression case, not permission to implement one now.
- **Confidence:** High for discarded metadata; medium-high for the unexecuted constructed output. **Strongest counterargument:** The research promises observed evidence, not a complete historical database, and `source: retained`/`last_error` still help. The defect is the stronger inference from packet flags or absent blockers, not failure of bounded journal queries themselves.

### Inferences

- No high-severity finding overturns the local capability inventory. “Existing primitives exist” is well supported; “their complete public contract is uniformly machine-safe and dependable” would overstate this evidence. The report itself explicitly calls its baseline non-certifying and its pilot proposed, which limits the damage ([R:5,9,71–83](../../reports/Agent%20workflow%20opportunities%20and%20validation.md#L5-L9)).
- The two documentation contradictions the research actually identifies are real; the adversarial review does **not** replace them with invented feature gaps. See ledger C30.

### Gaps

- F1–F3 were established from source and existing assertions, not by newly executing the counterexamples. No new tests, temporary reproducer code, services, or product/config edits were authorized or made.
